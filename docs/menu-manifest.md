# Service menu manifest

Status: partly implemented. The menu UI and `menuTabs()` exist; the manifest/builder part below is still a proposal (`TODO.md` section 5b)

## Goal

Adding a service (Discord bot, Syncthing, GitHub runner, a container) must not require editing or releasing the apps.
The service declares itself next to its NixOS configuration; both `hl` and `homelab-tui` discover it and render it in the menu with a per-service submenu of actions.

## Decision: data manifests, not executable modules

The first idea was a TypeScript module that exports the menu under a well-known Symbol, and the apps import it. That has two problems:

- A `Symbol` does not survive serialization. Anything fetched over ssh arrives as text, so the marker would be lost; `Symbol.for("...")` only helps inside one running process.
- Loading the manifest means executing code. `hl` runs on the desktop, so it would run whatever the server hands it. Data (JSON) can be validated; code cannot.

So the shipped format is **JSON with a marker field** (`"homelab": "menu/v1"`), which plays the role of the symbol: a file without it is ignored, and the version in it tells the parser which schema to use.

The symbol idea is still useful **inside the repo**: services bundled with the apps can be written in TypeScript with a typed helper, validated at build time and emitted as the same JSON shape.

```ts
// packages/core/src/menu.ts (planned)
export const MENU = Symbol.for("homelab.menu");

export function defineService(service: ServiceManifest) {
  return { [MENU]: true as const, ...validateManifest(service) };
}
```

## Where manifests live

On the server, one file per service: `/etc/homelab/menu.d/<id>.json`, generated by NixOS so it always matches the deployed config.

```nix
# nix-cfg/modules/homelab-menu.nix (planned): a small option that writes the file
{ config, lib, ... }:
{
  options.homelab.services = lib.mkOption {
    type = lib.types.attrsOf lib.types.attrs;
    default = { };
  };
  config.environment.etc = lib.mapAttrs' (id: svc: {
    name = "homelab/menu.d/${id}.json";
    value.text = builtins.toJSON ({ homelab = "menu/v1"; inherit id; } // svc);
  }) config.homelab.services;
}
```

```nix
# nix-cfg/modules/syncthing.nix
homelab.services.syncthing = {
  label = "Syncthing";
  description = "File sync, web UI on :8384";
  kind = "systemd";
  unit = "syncthing.service";
};
```

Deploying (`hl deploy`) updates the manifests, so the menu changes without a new app release.

## Schema (v1)

```json
{
  "homelab": "menu/v1",
  "id": "discord-bot",
  "label": "Discord bot",
  "description": "Monorepo bot, runs in Docker",
  "kind": "docker",
  "container": "discord-bot",
  "actions": [
    {
      "id": "migrate",
      "label": "Run migrations",
      "command": ["docker", "exec", "discord-bot", "bun", "run", "migrate"],
      "sudo": false,
      "tty": false,
      "danger": false
    }
  ]
}
```

- `kind`: `systemd` (needs `unit`) or `docker` (needs `container`).
- **Standard actions come from `kind`**, so the manifest does not repeat them: status, start, stop, restart, logs (follow), and for systemd enable/disable. `actions` only lists extras.
- `command` is an **argv array**, never a shell string. Core quotes it; nothing is interpolated.
- `sudo: true` forces a TTY so the password prompt appears (sudo always asks).
- `danger: true` asks for confirmation first.

## Validation rules

Reject (and show a readable message naming the file) when: `homelab` marker or version is unknown, `id` is not `^[a-z0-9][a-z0-9-]*$` or duplicated, a field is unknown, `unit`/`container` is missing for the `kind`, or `command` is not a non-empty string array. One bad manifest never hides the other services.

## Reading the manifests

- `hl`: one ssh call that prints all manifests plus live state (`systemctl is-active`, `docker ps`), parsed locally. Nothing from the server is executed on the desktop.
- `homelab-tui`: reads `/etc/homelab/menu.d` and queries state locally.
- Both use the same parser and menu component from `@homelab/core`, so a service appears in both.

## Menu shape

- Top level: general items (deploy, rebuild, reboot, ...) then every service with its live state (running / stopped / failed).
- Selecting a service opens a submenu: header with state, standard actions, extras, "Back".
- CLI mirror generated from the same data: `hl service <id> <action>`.

## Adding a service (once implemented)

1. Add `homelab.services.<id> = { ... };` in the service's module in `nix-cfg`.
2. Push, run `hl deploy`.
3. Open `hl`: the service is in the menu.

## Revision: builder API and `features/services/`

Idea: a small builder (factory) in `@homelab/core` so a service is defined in code, and one folder per service:

```ts
// features/services/syncthing/index.ts
export default defineService("syncthing")
  .label("Syncthing")
  .systemd("syncthing.service")
  .subtitle("web UI :8384")
  .details(["File sync", "Data in /data/syncthing"])
  .action("rescan", {
    label: "Rescan folders",
    command: ["syncthing", "cli", "operations", "rescan"],
  })
  .build();
```

`features/services/index.ts` collects the default export of every folder (generated, so adding a folder is enough) and `menuTabs()` renders them in the Services tab, with the standard actions derived from the kind.

Two ways to ship the definitions, which is the open decision:

|                               | Bundled in the apps                      | JSON written by NixOS (above)                     |
| ----------------------------- | ---------------------------------------- | ------------------------------------------------- |
| Add a service                 | New folder, merge to `main`, `hl update` | `homelab.services.<id>` in `nix-cfg`, `hl deploy` |
| Typing and tests              | Full TypeScript, unit tests              | Parsed and validated at runtime                   |
| Service and menu in one place | Only if `nix-cfg` is in the same repo    | Yes (same Nix module)                             |

If `nix-cfg` moves into this monorepo, each `features/services/<name>/` folder can hold both `index.ts` (menu) and `module.nix` (the NixOS service), so one commit changes both and nothing can drift. The builder can then also emit the JSON manifest, which keeps the "no app release" path open.
